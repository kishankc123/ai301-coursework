# Rubric: is this reproduction package ready to post?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| Environment recorded | The repro report's environment line/section (tool version, OS, relevant runtime/driver), read against the issue's stated target version in the issue context or repo-facts block. | The report names the tool version and OS (plus any runtime the issue's platform makes load-bearing, e.g. a driver on a driver-specific bug). If the named version differs from the one the issue was filed against, the report says so explicitly. Fails on a missing environment record, or on a silent version mismatch (a different version used with no acknowledgment). | required |
| Steps followable | The repro report's steps, read as commands or actions a stranger with only the repo and the report could carry out, from a named starting state to the trigger. | Every step needed to reach the trigger is present and could be run by someone else: no reliance on private, unshared state (a private monorepo, an unlisted config file, a machine-specific path) and no missing step that the issue's platform requires (e.g. a driver flag on a platform-specific bug). Fails if a stranger could not place or repeat the attempt from what is written. | required |
| Faithful trigger | The steps and artifact (output excerpt, log, screenshot) in the repro report, read against the exact input/trigger condition and failure mode the issue describes. | The report engages the same trigger the issue names (same syntax, same input shape, same operation), not an adjacent one substituted for it (wrong flag, wrong argument shape, an older version's already-different behavior). This check does not require the bug to have manifested — a faithful attempt at the same trigger that did not reproduce still passes here; whether the report is honest about that outcome is graded separately below. Fails when the artifact demonstrates a different trigger or a different failure mode than the issue describes (a graceful error standing in for a reported crash, or vice versa). | required |
| Honest conclusion | The report's stated conclusion (reproduced / did not reproduce / partial), read against what the shown artifact actually demonstrates. | The conclusion claims no more than the artifact shows. A confident "reproduced" needs an artifact that actually shows the issue's failure mode. An honest "could not reproduce" is a full pass when it names what was tried, what happened instead, and (where possible) what might differ from the reporter's setup. Fails when the words claim a result the artifact does not back — narrating a crash over an artifact that shows normal completion, or asserting a result with no artifact at all. | required |
| Comms are specific | The text of the claim comment and the repro comment (the drafts in live mode; the candidate comments in eval mode), read on their own, independent of the report's technical quality. | Each comment names the specific issue and a concrete, non-generic statement of intent or finding — not interchangeable boilerplate ("+1", "same here", "assign me", a guaranteed fix by a specific date). A terse comment can pass if what it says is concrete to this issue; length and template-shape are never the test. Fails on a comment that could be pasted onto a different issue unchanged, or that promises a fix/date rather than the investigation this package covers. | required |
| AI-use disclosure | The repo-facts block's stated contribution policy (does it require disclosing AI assistance?), read against whether the claim comment or repro comment discloses AI assistance. | Passes automatically if the repo's stated policy carries no AI-disclosure requirement. When the repo's stated policy does require disclosure, passes only if a comment discloses AI assistance; course packages are treated as AI-assisted work for this check, so silence where disclosure is required is a fail regardless of how strong the rest of the package is. | required |

## Verdict rule

Accept only if every required check above passes. A `fail` on any required check holds the package at `reject`, regardless of how the other checks graded — there is no partial credit and no check outweighs another. `unclear` is treated as `fail`: evidence that cannot be verified from the package is not evidence a stranger reading the same package could confirm either, so it cannot support posting.
